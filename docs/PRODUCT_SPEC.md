# CareerCopilot 产品规格说明书 (PRODUCT_SPEC)

## 1. 用户是谁

*   **目标用户**：正在参加秋招或春招的中国应届毕业生（本科生、硕士及博士），求职范围覆盖中国大陆、香港、美国、英国、新加坡等地。
*   **用户画像**：
    *   **高频投递者**：每天需要浏览大量岗位信息，并重复填写相似的表单。
    *   **信息焦虑者**：因投递公司过多而忘记进度，错过笔试或面试通知，或对类似岗位的不同 Offer 难以抉择。
    *   **效率导向者**：愿意使用开源工具来提升效率，希望掌控自己的求职数据，注重数据隐私（简历不外泄）。

## 2. 使用场景

*   **场景一：多地区机会整理与覆盖检查**
    *   用户持有覆盖多地区、多来源的机会数据集（XLSX，含 7 个工作表）。用户希望按工作表导入，快速查看所有机会，并检查目标公司是否至少有 3 个候选机会。
*   **场景二：区分项目入口与具体岗位投递**
    *   数据中既有校招项目/统一入口（campaign），也有具体岗位（job）。用户希望在界面上明确区分二者：campaign 需进入官网选择具体岗位，job 可直接投递。
*   **场景三：进度追踪与复盘**
    *   投递后，用户在笔试、面试、Offer 等不同阶段手动更新状态，形成可视化的求职进度看板。

## 3. 核心问题

*   **问题 1：信息过载与多布局兼容**
    *   源数据覆盖多地区、多来源，且同一工作表存在历史布局变体，缺乏一个能按工作表分发解析、自动识别布局的工具。
*   **问题 2：项目入口与具体岗位混淆**
    *   campaign 与 job 混在同一表中，用户难以区分“还需进官网选岗位”和“可直接投递”的机会。
*   **问题 3：状态管理混乱**
    *   随着投递数量的增加，用户很难准确记忆每个公司的投递状态。
*   **问题 4：公司覆盖度不明确**
    *   用户无法一眼看出哪些目标公司的候选机会较少。

## 4. MVP 0.1 范围 (In Scope)

本阶段产品将聚焦于构建一个轻量级的**机会管理看板**，实现以下核心闭环：

*   **多工作表导入与去重**
    *   支持导入多工作表 XLSX 与 CSV。
    *   按工作表选择解析器，自动识别中国大陆 sheet 的新版/旧版布局（依据 F 列是否为招聘类型关键词）。
    *   对无法自动判定的记录保留 `raw_data`，导入预览时交由人工确认。
    *   导入前向用户展示：新增、重复、无效、待人工确认的数量。
*   **机会浏览与类型区分**
    *   以卡片或列表形式展示机会信息。
    *   **campaign 与 job 必须视觉区分**（不同标签/颜色）。
    *   支持按公司、地区、记录类型、状态等多维筛选。
*   **候选清单与公司覆盖检查**
    *   **始终展示全部机会**：系统保留并展示每家公司的全部机会，**不设置上限**。
    *   **按优先级排序**：候选清单按 `priority` 排序，并**默认突出显示前 3 个**机会（重点展示，**不是截断**）。
    *   **候选清单可超过 3 个**：用户可将 3 个以上机会加入候选清单，任何视图都不得因为“前 3”而隐藏其他机会。
    *   **覆盖缺口提示**：当某公司候选机会少于 3 个时，显示数量缺口（如“差 1 个”）。
    *   对**只有 campaign、没有具体 job** 的公司，显示“需进入官网选择具体岗位”。
    *   **MVP 0.1 不承诺**从 campaign 拆出三个具体岗位；“每家公司至少推荐三个具体岗位”仅在 MVP 0.2 获取明确岗位信息后执行。
*   **投递执行与状态追踪**
    *   提供“投递”按钮，**点击仅跳转链接，状态标记为 `opened`**。
    *   **必须由用户手动确认**才能将状态标记为 `applied`（已投递）。
    *   提供完整状态流转（discovered -> ... -> withdrawn）。
*   **数据持久化**
    *   使用本地 SQLite 数据库存储数据。

## 5. 非 MVP 范围 (Out of Scope)

*   **简历解析与智能匹配**：MVP 0.1 不涉及任何形式的简历与岗位匹配算法；也不从 campaign 自动拆解具体岗位。
*   **自动投递**：使用 Playwright/Selenium 自动填写表单并提交。
*   **邮件自动获取**：通过 Gmail API 自动拉取和解析招聘邮件。
*   **多用户系统**：仅支持本地单用户使用。

## 6. 用户操作流程

1.  **启动应用**
    *   用户运行 `streamlit run app.py` 启动本地服务。
2.  **按工作表导入机会表**
    *   用户上传 XLSX/CSV，选择目标工作表。
    *   系统按工作表分发解析器，识别布局（新版/旧版/未知）。
    *   对未知布局或待确认记录，用户在预览阶段人工确认记录类型与字段映射。
    *   系统报告导入结果（新增/重复/无效/待确认）。
3.  **浏览与覆盖检查**
    *   **全量视图**：查看所有机会，campaign 与 job 区分展示。
    *   **候选清单视图**：查看每家公司**全部已排序机会**（按 `priority` 排序），默认突出显示前 3 个（不截断，其余机会仍可见）；不足 3 个显示数量缺口；只有 campaign 的公司提示“需进入官网选择具体岗位”。
4.  **投递与状态管理**
    *   点击“投递”按钮 -> 浏览器跳转（campaign 打开 `application_url` 或 `announcement_url`；job 打开 `application_url`），状态变为 `opened`。
    *   **投递完成后，用户需手动点击“确认已投递”按钮**，状态才变为 `applied`。
    *   根据笔试、面试进展，手动更新后续状态。

## 7. 验收标准

*   **核心功能**
    *   能成功导入包含至少 100 行数据的多工作表 XLSX 与 CSV。
    *   能按工作表选择解析器，并正确识别中国大陆 sheet 的新版/旧版布局。
    *   对无法判定的记录保留 `raw_data` 并允许人工确认，不强行推断；**`unknown` 记录不写入数据库**，须由用户在导入预览确认为 `campaign`/`job` 后才入库（`opportunities.record_type` 只存 `campaign`/`job`）。
    *   能准确识别并报告新增、重复、无效、待人工确认机会的数量。
    *   同一文件重复导入，不会创建重复的机会记录。
    *   应用重启后，所有状态和优先级变更依然保留。
    *   **点击链接不会自动标记为“已投递”**，必须用户手动确认。
    *   候选清单视图始终展示每家公司全部机会，按优先级排序并默认突出前 3 个（不截断）；机会少于 3 个时显示数量缺口。
    *   对只有 campaign 的公司，界面明确提示“需进入官网选择具体岗位”。

*   **用户体验**
    *   campaign 与 job 在界面上视觉区分清晰。
    *   操作闭环：完成从导入 -> 筛选 -> 跳转 -> 更新状态的全流程。

*   **健壮性**
    *   导入缺少必要字段的记录时，能给出清晰的错误提示，并计入“无效”统计。
    *   应用崩溃或重启不应导致数据库损坏。

*   **性能参考（非阻塞）**
    *   在 1000 条数据规模下，筛选和列表渲染的响应时间 < 1 秒。此条作为性能参考，不作为 MVP 0.1 阻塞性验收条件。
